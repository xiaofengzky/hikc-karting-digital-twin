# 2026-10-19

## HIKC 孝感国际卡丁车赛车场 · 3D 数字孪生（WebGL 单文件）

**产物**：`HIKC_孝感卡丁车赛车场.html`（约 780KB，Three.js r157 已内联，离线可开）

**数据来源（关键）**
- 真实赛道中心线来自用户提供的 Racebobo VBO 遥测：`湖北国际卡丁车_2026-09-06_18_32_17.vbo`
  - 25Hz，8 个完整圈，圈长 1241–1275m，8 圈平均后中心线周长 **1233m**（官方标称 1240m）
  - 高程取自 GPS height 字段，归零后高差约 2m
- **镜像修正**：初版轨迹南北反了。用 heading 与轨迹切线方位角比对（diff 恒定 180°）确认，`z = +(lat-lat0)` 才对
- 卫星俯视图（用户提供）用于校正主直道朝向与 P 房位置

**场景结构**
- 赛道：centerline 采样 620 点/2m，条带生成路面 + 蓝白路肩（现场照片是蓝白，不是红白）+ runoff
- 起跑线棋盘 + 12 个发车格（沿行驶方向正 s 排布）
- 布局层次：**P房/售票楼（含二层观景平台）→ 水泥停车区/围场（32 台卡丁车）→ 赛道**
  - 注意：主直道实际**向西**行驶，所以赛道外侧是 `+nrm`，不要用 `-nrm`
- 周边：王母湖（东）、澴河（西）、奥体东路（西）、奥体中心体育场、城南大道（南，推远 332m）
- 天气：8 种预设 + 平滑插值；雨/雪 GPU 粒子；水 shader 带雾
- 赛道湿滑演进：`S.wet` 由降雨浸润 vs 日照/温度/风蒸发驱动，联动 roughness/metalness/envMap + 抓地力读数

**踩过的坑（重要经验）**
1. `stripGeometry` 闭合段 UV 必须用索引 i 计算，不能用 TRACK.s[k]，否则纹理 v 回绕把路面拉出一条白线
2. Three.js Euler 组合（rotation.x + rotation.z）会把平面立起来 → 用 Group 承载朝向，子物体只转 rotation.x
3. 高程必须归零，VBO 的 height 是海拔（21m），不归零会导致相机/建筑全部算歪
4. 广告牌双面用「两片单面 plane 背靠背」，比 DoubleSide 稳（背面不镜像）
5. 道路虚线的 `rotation.z = PI/2` 会把 620m 长条横穿整个场地

**工具链**（part 拼装）
- `tools/vbo_parse.py` → `vbo.npz`；`vbo_lap2.py` → 多圈平均；`gen_data2.py` → `track_data.js`
- `parts/*.js` 分模块，`parts/build.py` 合并 + 内联 three.js
- `tools/test.js` puppeteer-core + Edge 无头截图回归

## 三个 bug 修复（10-20 第八轮）
1. **自由漫游点一下画面消失**：`presetView('fly')` 里 `CAM.yaw = atan2(d.x,d.z) + Math.PI` 多转了 180°，
   相机一进 fly 就朝背后看 → 表现为"画面不见了"。去掉 `+Math.PI` 即可。
   方向约定：`fwd = (cos(pitch)*sin(yaw), sin(pitch), cos(pitch)*cos(yaw))`，反解 `yaw = atan2(d.x, d.z)`。
2. **T1 位置不对**：gen_data2 的弯道峰值判定阈值 `R < 130m` 太严，而主直道尽头那个弯 R≈150–450m，
   被当成直道跳过了，导致 T1 落到了 s=360 的后续弯。放宽到 `R < 560m` 后识别出 **17 个弯**（与官方标称一致），
   T1 正确落在 s=106 的主直道尽头。
3. **阴天天空全是方格**：两个原因 ——
   - `hash()` 用 `fract(sin(dot(p,vec2(127.1,311.7)))*43758.5)`，大值时 sin 精度丢失产生网格伪影
   - 云层 `cuv = d.xz / max(up*0.85+0.16, 0.055)`，地平线附近 UV 爆炸 → 高频摩尔纹
   修法：换成 `p=fract(p*vec2(123.34,456.21)); p+=dot(p,p+45.32)` 的稳定 hash；
   UV 下限 0.055→0.18 并做 `cuv/(1+len*0.05)` 软压缩；`smoothstep` 加 `hi = max(lo+0.22, ...)` 下限保护。
- 路肩 span 调为 `clamp(R*0.68, 11, 19)`（17 个弯时避免互相重叠铺满全程）。
- 周边按高德卫星图补：场地北侧东西向道路（连体育中心停车场）。

## 入口支路终于可见（10-20 第十四轮）
支路"看不见"叠了三层原因，逐个修：
1. **地形走廊太窄**：`|x-168|<34` 只覆盖主干道，支路 x∈[94,168] 大部分在走廊外。
   → 新增独立支路走廊 `(1-smoothstep(14,26,|z-8|)) * (1-smoothstep(84,104,|x-126|))`，压平到 -0.95。
2. **地形网格分辨率**：格距 ≈9.9m，比路宽 9.5m 还大，走廊边界容易落在顶点之间。→ 走廊放宽到 ±14m。
3. **行道树挡路**：buildTrees 没排除道路区域，树正好长在支路上。
   → 加排除：`|x-168|<22` 和 `|z-8|<13 && x∈(80,180)` 不种树。
4. 支路抬高到 y=-0.45（高出地形 0.5m），并做了**专用双车道纹理**（白边线 + 中央虚线，repeat 1×3），

⚠️ 验收教训：这类"有对象但看不见"的问题，要按 地形高度 → 网格分辨率 → 遮挡物 → 纹理 的顺序排查。

## 换上真卡丁车模型（10-20 第十八轮）
第二个包 `卡丁车3(Go Kart 3)` 里有 **OBJ + GLB + glTF**，可用 OBJ 直接解析。
`tools/obj2kart.py` 流程：
1. 按 `g` 分组解析 v/f（body_msh 15180 tris / wheels_msh 6880 tris，共 11862 顶点），四边面三角化
2. **坐标轴转换**：原模型是 3ds Max 的 Z-up（y=车长 168.39cm、x=车宽 124.8、z=高 50.48）
   → 转 Y-up：new_x=原y, new_y=原z, new_z=原x，并缩放到车长 1.8m
3. **Int16 量化**（1/10000 m 精度）+ 索引 Uint16 + base64 → 共 271KB，inline 进 HTML
4. `decodeKartMesh()` 在浏览器里解码成 BufferGeometry，`computeVertexNormals()`
5. ⚠️ **OBJ 绕序与 Three 相反**，必须翻转索引三元组，否则法线朝内、车身看起来半透明
6. 2 个 InstancedMesh（车身/轮子）承载 18 台；材质 `0xd9e4f4 / metalness 0.26 / DoubleSide`

## 车辆消失事故 + 修复（10-21 第二十六轮）
用户反馈"门口水泥地和赛道上的车全都不见了"。
**根因**：上一轮给停放车加涂装时调用了 `mergeGeoList`，但那个函数在早前重写 buildKarts 时被一起删掉了。
于是 `buildKarts` 抛 `ReferenceError: mergeGeoList is not defined`，

**教训（重要）**：

   每次 build 后应抓一次 `pageerror` / `console.error`，而不是只看截图。
3. 一个模型丢失往往意味着**整批**丢失（因为都在同一个 LOAD_STEPS 步骤里），

4. **车位线与车错位**：
   - 车位线用 Mesh 逐个画（InstancedMesh 的 rx/rz 组合参数没按预期生效，导致线方向乱）
   - 车的 x 公式错用 `(c-(COLS-1)/2)*BAY_W`，偏移了半个车位 → 改成 `x0 + c*BAY_W`

## 水泥停车区贯通赛道（10-22 第三十一轮）
用户澄清：不是停车场，是 **P 房前停卡丁车的水泥区（paddock）**，两个问题：
1. 这块地有一部分被草地穿透（绿色斑块）
2. 水泥区与赛道之间隔着草地，进不了赛道

修法：
- **草地穿透**：原来是 `PlaneGeometry(86,24)` 单层平面，y = terrainHeight + 0.06，
  而地形在该处起伏超过 0.06 → 草穿过地面。改成 **BoxGeometry(86, 0.72, 34.5)**，
  中心 y = -0.31（顶面 +0.05、底面 -0.67 埋进地形），有厚度就不会被草穿透。
- **连不到赛道**：原来中心在 `trackFrame(22, 6+23)`（距中心线 29m），内侧边缘离路肩还有 11m 草地。
  改成中心 `trackFrame(22, 25)`、宽 34.5（法向 7.75~42.25），内缘直接顶到路肩。
- 配合上一轮 `buildFences` / `buildBarriers` 在 s∈[6,46] 的开口，现在水泥区可以直接开上主直道。

⚠️ 地面铺装类物件：**用有厚度的 Box 比用单层 Plane 稳**，Plane 极易被地形起伏穿透，
尤其是这种地形网格 5m 一格、周边有噪声起伏的区域。

## 水泥区改条带 + 清广告牌（10-22 第三十二轮）
上一轮用 BoxGeometry 加宽，看似连到赛道，实际还有楔形草地——**因为矩形板不跟随赛道弯曲**，
而赛道在主直道两端有弧度，板的内缘和路肩之间就露出了草地。

改法：
- **水泥区改成 strip**：沿 s∈[-24,66] 每 2m 采样，A 点取 `hw+0.12`、B 点取法向 41，
  用 `trackAt` 的 nrm 生成条带，内缘全程贴着路肩，边缘跟着赛道走。
- **地形补维修区平台**：`smoothstep(72,79,z)*(1-smoothstep(108,118,z))` ×
  `smoothstep(-92,-82,x)*(1-smoothstep(44,54,x))`，压到 -0.18，避免草穿透条带。
- **广告横幅**：`buildBanners` 的循环加 `if (s>4 && s<48) continue`，
  维修区出口段（HIKC/VEGA/CKC 那排）不再有牌子挡路。

⚠️ 凡是"贴赛道"的地面/围挡，都要用 `trackAt(s)` 沿 s 采样成条带，
   不能用对齐到某个 s 的矩形 box —— 矩形只要离开采样点就会和赛道错开。

## 卡丁车高度 / 门架红灯（10-22 第三十三轮）
1. **水泥区的卡丁车全消失**：`buildKarts` 用 `terrainHeight(F.p.x, F.p.z)` 取地面高度，
   但上一轮为了消除草穿透，把维修区地形压到 -0.18，而水泥面在 `trackAt(22).p.y + 0.07`，
   车就落到铺装面**下方**被埋掉。
   修：`const gy = trackAt(22).p.y + 0.09;` —— 直接用水泥面高度，不再查地形。
   ⚠️ 压平地形后，所有依赖 `terrainHeight` 的物件都要改到铺装面高度。
2. **门架红灯"反了/看不见"**：灯在 `beamY - 0.85`，而横梁底在 `beamY - 0.46`，灯被包在横梁内部；
   同时只有 z=+0.34 一侧有灯。
   修：计时盒与灯一起下移到 `beamY - 1.15`（横梁下方悬挂），灯改成 **z=±0.34 双面**，
   半径 0.11→0.14，`emissiveIntensity` 1.6→4.0、`emissive` 纯红 0xff0000。

## 发车灯终于可见（10-22 第三十四轮）
用户正面视角截图确认：黑盒子上一个红灯都没有。
之前的做法（`MeshStandardMaterial + emissive`）在这个场景里根本看不出来 ——
可能被横梁/盒子遮挡，也可能是 PBR 的 emissive 在 ACES 色调映射下被压没了。

改法：**换成 `MeshBasicMaterial({ color: 0xff1a1a, side: DoubleSide })` + `CircleGeometry(0.15)`**，
纯色面片不参与光照与色调映射，正反两面各贴一片（z = ±0.315）。
同时黑盒子从 1.7×0.75 调整为 2.1×0.62，灯横向间距 0.42。

实测正面 30m 处能清楚看到横梁下的红点。

💡 经验：**小尺寸的"发光小物件"不要用 emissive 材质**，在这个场景的曝光/色调映射下会被吃掉；
   用 `MeshBasicMaterial` 纯色面片最稳，代价是没有辉光（要辉光得加 sprite 或后期）。

## 发车灯朝向修正（10-22 第三十五轮）
用户澄清"反了"的真正含义：**灯要朝发车格（来车方向），不是朝另一侧**，不是"看不见"。
`buildStartGantry` 的 group 用 `rotation.y = -a + PI/2`，此时局部 **+z = 切线正方向（行驶方向）**，
所以来车方向是局部 **-z**。
修：灯只保留一片，位置 `z = -0.315`、`rotation.y = PI` 让它朝 -z，删掉 +z 侧那组。
现在从发车格方向（西侧）能看到 4 颗红灯，绕到 P 房那一侧则看不到 —— 符合真实发车门架。

💡 门架/招牌类朝向判断：`rotation.y = -a + PI/2` 时，局部 +z 沿赛道前进方向、+x 沿横向法线。

## 发车灯朝向（最终，10-22 第三十六轮）
之前把"哪一面"搞混了：赛道 s 增加方向是**向西**（起点 x=20、主直道尽头 x=-95），
所以发车格（s 为负）在**东侧**，门架也在东侧；从发车格往赛道里看是**朝东**。

用户两张图分别是"朝东看"（发车格侧，应看到灯）和"朝西看"（赛道另一头，看不到）。
最终把灯放回 **局部 +z 面（`z=+0.315, rotation.y=0`）**，从发车格方向可见、反向不可见。
同时把灯放大：`CircleGeometry(0.22, 16)`、间距 0.50、黑盒 2.5×0.72。

## ⚠️ 严重教训：patch 打错文件（10-22 第三十七轮）
用户说"根本没改"——查证后发现**前四轮关于发车灯的修改全部无效**：
`buildStartGantry` 定义在 **`p5_trackfx.js`**，而我一直在 `p6_buildings.js` 里找同样的字符串，
`str.replace()` 找不到就静默返回原串，我的脚本还照样打印"lamps xxx"，等于自己骗自己。

**教训（必须遵守）**：
1. 改任何函数前，先 `grep -n "function xxx" parts/*.js` 确认它在**哪个文件**。
2. `str.replace()` 后必须校验：`assert old in s` 或比较替换前后长度，否则等于没改。
3. 用户说"没改"时，第一件事是 `grep` 目标代码确认现状，而不是再改一遍。

最终在 p5 生效的版本：
- 灯：`MeshBasicMaterial({color:0xff1a1a})` + `CircleGeometry(0.24,16)`，z=+0.315，间距 0.60
- 黑盒：2.5×0.72×0.6，y = beamY-1.15（横梁下方悬挂）
- 实测：朝东看（发车格/主直道方向）4 颗红灯清晰；朝西看背面全黑。
